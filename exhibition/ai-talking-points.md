# Reminq × 生成AIなんでも展示会 — 説明用トーキングポイント

LLM イベント来場者向け。**「LLM 時代のプロダクトは構造そのものが違う」**という視座から、Reminq を 1 つの実例として語る。展示プレート (`exhibition/reminq-ai-exhibition-plate.pptx`) の補助資料。

---

## Reminq とは

Apple 標準のリマインダーを **LLM が読み解いてカンバンで動かす** iOS / iPadOS / macOS アプリ。
雑に書いた 1 行を、実行可能なステップ群 + 優先度に展開する。ユーザーは下案を選ぶだけでよい。

---

## 中心仮説

> ソフトウェアは長らく「**入力 → 保存 → 表示**」の 3 層だった。
> LLM 以降、その間に「**解釈**」と「**採否**」という 2 層が入る。
> プロダクトの役割は「入力を実行する」から「**入力を読み解く**」に移る。

Reminq はこの仮説を、Apple のリマインダーという誰もが持っている題材で検証している実装。

---

## LLM 以前のプロダクトは何を要求していたか

- ユーザーが**入力する前に考え終えていること**を要求していた
  - 「資料を作る」では雑すぎる、と人間に突き返していた
  - 粒度・順序・優先度はすべてユーザーの脳内で完了している前提
- 結果、プロダクトは**整理が終わった人**にしか使われなかった
  - リマインダー、ノート、カレンダー、Issue トラッカー — どれも同じ構造
  - 雑な思考をそのまま受け止める層がなかった

これは「ソフトウェアは正確な入力を要求する」という、コンピューティング 60 年来の前提だった。

---

## LLM が変えたのは「機能」ではなく「層構成」

LLM の本当の効きどころは、便利機能を 1 つ増やすことではない。**プロダクトの層を 1 段増やす**ところにある。

```
[ LLM 以前 ]              [ LLM 以降 ]

入力                      入力（雑でよい）
  │                         │
  ▼                         ▼
保存                      解釈     ← LLM が引き受ける
  │                         │
  ▼                         ▼
表示                      採否     ← 人間が引き受ける
                            │
                            ▼
                          保存
                            │
                            ▼
                          表示
                            │
                            ▼
                          振り返り ← データから次の解釈へ
```

この 2 層が増えると、プロダクトが**ユーザーに要求するもの**が変わる：

- ユーザーは**整理を終えた状態で来なくてよい**
- 雑に投げて、出てきた下案を**選ぶ / 直す**だけでよい
- 認知負荷が「**考える**」から「**選ぶ**」に移る — これが体験の本質的変化

「LLM が答えを出してくれる」ではない。**「ユーザーが雑でよくなる」**ことが LLM 時代のプロダクトの本体。

---

## Reminq での層の置き方

### 解釈層

- 入力は雑な 1 行（例: 「資料を作る」）または紙の付箋の写真
- LLM が**ステップ群 + 各ステップの優先度**を 1 ショットで返す
- 分解と優先度付けを別呼び出しに分けない — **順序の根拠を持ったまま優先度を付けさせる**ためのプロンプト設計
- ここが「**入力に対する解釈**」を担当する層

### 採否層

- LLM 出力はリマインダーへ直接書き込まれない
- チェックされた項目だけが静かに反映される
- これは「AI が間違うから」の安全機構ではない。**ユーザーが雑に書けるようにするための誘導装置**
- 「採否は軽い」という前提があるからこそ、入力の質に対する要求を下げられる
- 結果として **LLM の不完全さがプロダクトの構造に組み込まれ、完璧でなくても破綻しない**

### 振り返り層

- カンバン × アクティビティ解析で「止まりやすい型」が可視化される
- 解釈 → 採否 → 実行 → 観測のループが閉じる
- 「曖昧に書きすぎるタスク」「粒度が大きすぎるタスク」が**データで識別できる**ようになる

---

## なぜこの視座が LLM イベントで語る価値があるか

- LLM 系プロダクトの議論は「どのモデルか / どう呼ぶか」に流れがちだが、そこは**入れ替え可能な詳細**
- 本当の設計問題は次の 2 問:
  1. **解釈層をプロダクトのどこに挿すか**
  2. **採否層をどう設計するか**（LLM の不完全さをどこで吸収するか）
- この 2 問に答えれば、タスク管理に限らず**ノート・カレンダー・Issue・コードエディタ・検索**、あらゆる「入力を待つプロダクト」が再設計できる
- Reminq はその 1 つの解。**雑な日本語を「動ける単位」に翻訳する層**が、ユーザーの入力習慣そのものを変えていく

---

## 想定 QA（視座を保ったまま）

- 「これはタスク管理アプリの話？」 → タスク管理は題材。本質は **LLM 時代の層構成**の話
- 「LLM が間違ったら？」 → 採否層で吸収される。**間違いがプロダクトを破綻させない構造**を最初から組んである
- 「他のプロダクトに転用できる？」 → 「入力を待つプロダクト」全般に適用可能。同じ層構成でノート・カレンダー・Issue・検索が再設計できる
- 「LLM をリプレースしたら体験はどうなる？」 → 解釈層だけが入れ替わる。データも UI も触らずに静かに賢くなる
- 「ユーザー側の何が変わる？」 → 整理してから書く → **雑に書いて選ぶ**。考えるコストが選ぶコストに置換される
