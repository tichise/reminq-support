## Reminq とは

iOS / iPadOS / macOS 向けのタスク管理アプリ。Apple 標準のリマインダーをカンバンで動かす。

Reminq の入力は**雑でよい**。次のいずれでも受け付ける：

- **1 行の大きなタスク** — 例: 「資料を作る」「引っ越しの準備」「確定申告」
- **やることの候補リスト** — 頭に浮かんだものをぱらぱら書き並べただけのメモ
- **紙の付箋・手書きメモの殴り書き** — カメラで撮影して投入

LLM がこれらを読み取り、**実施に必要なタスク（リマインダー）の集合**に分解・整理して、各タスクに優先度ラベルを付けた下案を返す。ユーザーがチェックしたものだけが Apple リマインダーに追加され、カンバン（TODO / 進行中 / 完了）でドラッグして動かせる。

```
入力例: 「資料を作る」 / 候補リスト / 付箋の写真

         │ LLM が読み取り → 必要なタスクに分解・整理
         ▼

出力（下案）:
  ☐ 目次を 5 行で書き出す              [High]
  ☐ 参考資料を 3 件集める              [Mid]
  ☐ 結論スライドを 1 枚先に作る        [High]
  ☐ 空白スライドにタイトルだけ並べる   [Low]

         │ ユーザーがチェックで採否
         ▼

採用されたものが Apple リマインダーに追加される
→ カンバン（TODO / 進行中 / 完了）でドラッグして動かす
```

ユーザーがやることは **「雑に出す」と「チェックする」** だけ。粒度・順序・優先度の判断は、すべて LLM が下案として担当する。

## 中心仮説 — LLM 時代の層構成

> LLM 時代のプロダクトは「**入力 → 解釈 → 採否 → 保存 → 表示 → 振り返り**」の 6 層で動く。
> ユーザーは雑に投げる。プロダクトが読み解き、人間は選ぶ。

中核は新しい 2 層 — **解釈** と **採否**。これがプロダクトに挿し込まれた瞬間、ユーザー側の負荷の重心が動く：

```
入力（雑でよい）
  │
  ▼
解釈     ← LLM が引き受ける
  │
  ▼
採否     ← 人間が引き受ける
  │
  ▼
保存
  │
  ▼
表示
  │
  ▼
振り返り ← データから次の解釈へ
```

- ユーザーは整理を終えた状態で来なくてよい
- 雑に投げて、出てきた下案を**選ぶ / 直す**だけでよい
- 認知負荷の中心が「**考える**」から「**選ぶ**」へ移る

「LLM が答えを出してくれる」ではない。**「ユーザーが雑でよくなる」**ことが LLM 時代のプロダクトの本体。Reminq はこの仮説を、Apple のリマインダーという誰もが持っている題材で検証している実装。

## Reminq での層の置き方

### 解釈層

- 入力は雑でよい — 1 行の大きなタスク / 候補リスト / 紙の付箋の写真、いずれも受ける
- LLM が**実施に必要なタスク群 + 各タスクの優先度**を 1 ショットで返す
- 分解と優先度付けを別呼び出しに分けない — **順序の根拠を持ったまま優先度を付けさせる**ためのプロンプト設計
- ここが「**入力に対する解釈**」を担当する層

### 採否層

- LLM 出力はリマインダーへ直接書き込まれない
- チェックされたタスクだけが静かに Apple リマインダーへ着地する
- これは「AI が間違うから」の安全機構ではない。**ユーザーが雑に書けるようにするための誘導装置**
- 「採否は軽い」という前提があるからこそ、入力の質に対する要求を下げられる
- 結果として **LLM の不完全さがプロダクトの構造に組み込まれ、完璧でなくても破綻しない**

### 振り返り層

- カンバン × アクティビティ解析で「止まりやすい型」が可視化される
- 解釈 → 採否 → 実行 → 観測のループが閉じる
- 「曖昧に書きすぎるタスク」「粒度が大きすぎるタスク」が**データで識別できる**ようになる

## CLI / MCP / エージェントとの関係

LLM プロダクトの主流である CLI / MCP / エージェント系も、根っこの構造は同じ — **LLM が読み解き、人間が採否する**。Reminq はその構造を Apple リマインダーという固有のドメインで実装しているだけで、対立する別物ではない。

**Reminq は CLI / MCP との連携機能を近日リリース予定**。外部のエージェントや MCP クライアントから Apple リマインダー上のタスクを参照・追加・分解依頼できるようになり、Reminq の解釈層を**他の LLM 文脈からも呼び出せる**ようになる。主流の形式と Reminq の固有 UI が繋がる方向。

## この視座の射程

LLM 系プロダクトの議論は「どのモデルか / どう呼ぶか」に流れがちだが、そこは**入れ替え可能な詳細**。本当の設計問題は次の 2 問：

1. **解釈層をプロダクトのどこに挿すか**
2. **採否層をどう設計するか**（LLM の不完全さをどこで吸収するか）

この 2 問に答えれば、タスク管理に限らず**ノート・カレンダー・Issue・コードエディタ・検索**、あらゆる「入力を待つプロダクト」が再設計できる。Reminq はその 1 つの解。**雑な日本語・候補リスト・付箋の写真を「動ける単位」に翻訳する層**が、ユーザーの入力習慣そのものを変えていく。

## 想定 QA

- 「これはタスク管理アプリの話？」 → タスク管理は題材。本質は **LLM 時代の層構成**の話
- 「LLM が間違ったら？」 → 採否層で吸収される。**間違いがプロダクトを破綻させない構造**を最初から組んである
- 「CLI / MCP との連携は？」 → **近日リリース予定**。外部のエージェントや MCP クライアントから Reminq の解釈層を呼び出せるようになる
- 「他のプロダクトに転用できる？」 → 「入力を待つプロダクト」全般に適用可能。同じ層構成でノート・カレンダー・Issue・検索が再設計できる
- 「LLM をリプレースしたら体験はどうなる？」 → 解釈層だけが入れ替わる。データも UI も触らずに静かに賢くなる
- 「ユーザーはどう振る舞う？」 → **雑に出して選ぶ**。考えるコストが選ぶコストに置換される
